**可以。现在把主线正式改成：固定100条mesh，使用同一个模型，从随机初始化开始做overfit。原来的单条804点精修不再是必须先通过的前置关卡。**

但“从头开始”应当是**重新初始化模型、Adam和训练计数，重新固定100条数据与实验协议**，不是丢掉已经定位好的数值实现，重新从hard loss、BF16不确定性等问题查起。

**眼下先做：固定100条清单 → 完成数据与资源预检 → 启动一条100-mesh μ重建基线。不要一开始同时加入sampling、KL、LoRA或新的权重策略。**

## 一、先把这次的目标写死

本次第一阶段的目标是：

> **固定这100条完整mesh，用同一套512维网络参数，通过正常端到端训练，在同一个checkpoint上把100条的Edge和实际Face全部重建正确。**

不是“任意100条都要很快成功”，也不是100份分别训练的模型，更不能把不同checkpoint各自最好的结果拼在一起。

每条仍然要求：

$$
\mathrm{EdgeFP}=\mathrm{EdgeFN}
=\mathrm{FaceFP}=\mathrm{FaceFN}=0.
$$

Face仍从该条mesh**当前预测Edge图**枚举，threshold=0，未进入候选的GT Face仍计FN。

### 100条的验收布局需要明确调整

我建议新协议采用：

**固定一个checkpoint，停止所有参数更新，分批完整评估100条，汇总是否100/100全部通过。**

这和最初两条的“单次packed forward”是不同的执行口径，必须在新协议中明确写出来，不能把分批验收称为“packed100成功”。**不变的是同一套权重、同一次全量验收、每条严格零错误。**

若仍要保留“物理上一次packed100”的额外要求，就需要单独验证它的资源可行性；不能默认单卡能装下，也不应把它和“一个模型能否记住100条”混为一谈。

## 二、第一件事：固定100条，不先启动长训

需要生成一个不可随训练表现改动的 `overfit100_manifest.csv`。

建议从目标训练数据范围内，**按顶点规模分层、用固定随机种子选择100条**。可以包含之前研究过的mesh，但必须记录，不能训练后挑出100条效果好的来交差。

清单至少包含：

| 字段                 | 用途                |
| ------------------ | ----------------- |
| mesh UID、数据路径与内容哈希 | 确保始终是同一批数据        |
| 顶点数、GT边数、GT面数      | 描述任务规模            |
| Edge pair总数        | 估计完整评分成本          |
| Face训练pool大小与哈希    | 固定监督集合            |
| 数据／候选校验结果          | 避免ID错位、重复、GT与负例冲突 |

**不要只挑100条最小、最容易的mesh。** 同时也不能不看资源范围，随意混入当前实现完全无法完整处理的超大mesh。允许的尺寸范围和数据有效性规则应提前确定，排除原因如实记录，而不是按照重建效果排除。

所有100条都做一次轻量数据校验：顶点索引合法、GT去重规则一致、GT边与面的对应正确、全部GT Face进入训练pool、负例不与GT冲突。

还要记录一个已知风险：**Face训练pool与实际预测候选不是同一个集合。** 上一轮末尾40个实际Face FP全部在训练pool之外，这一覆盖问题不能因为重新开始就忘掉。新基线暂时不改策略，但从第一轮评价就要分别记录训练pool与实际Face结果。

## 三、模型和loss沿用当前版本，只重新初始化

建议本次基线固定为：

| 项目             | 100-mesh新基线                           |
| -------------- | ------------------------------------- |
| 初始化            | **固定种子随机初始化，不加载旧checkpoint**          |
| Optimizer      | **fresh Adam**                        |
| Latent         | 每顶点512维                               |
| Decoder hidden | 1024维                                 |
| Edge／Face评分表示  | 各32维，原评分公式和scale                      |
| 重建路径           | **\(z=\mu\)**                         |
| Sampling／KL    | 关闭，β=0                                |
| 可训练范围          | Encoder＋μ、Decoder、Edge head、Face head |
| logvar专属参数     | 冻结并排除在optimizer之外                     |
| Backend        | **math00、确定性Graph、FP32 attention**    |
| Loss           | fully-diff Edge Soft4＋Face Soft4      |
| 其他             | wd=0、global clip=1、原betas/eps，无新增数据增强 |

这些模型接口、数值路径和loss定义都已有当前版本的配置记录，不需要重新猜测。**输入也保留实际实现中的顶点XYZ、Face centroid与incidence graph，不再沿用早期“整个模型无XYZ”的不准确概括。**  

第一阶段不引入LoRA、复杂度权重、成功embedding蒸馏或离线拟合head。它们现在不是100条基线的必要组成部分。

**继续使用512是本次的工程选择，不代表已经证明512优于64。**

## 四、100条不等于每次optimizer update必须处理全部100条

这是这次最需要重新设计的地方之一。

### 建议起点：有效batch为4条完整mesh

先采用：

* 每个microbatch处理一条完整mesh；
* 累积4条mesh的梯度；
* 然后统一clip一次、Adam更新一次；
* 每个epoch将100条打乱并完整遍历一次，不遗漏、不重复补齐。

这是**按mesh组成mini-batch**，不是把mesh切成子图。

假设当前一组有4条，优化目标是：

$$
L_{\rm batch}
=
\frac14\sum_{m\in\mathcal B}
\left(
L_{{\rm EdgeSoft4},m}
+
L_{{\rm FaceSoft4},m}
\right).
$$

**各mesh先独立完成Soft4归约，再对4条取平均。** 不把所有mesh的候选混成一个大池，让大mesh按候选数量压倒小mesh。

这里的外层 \(1/4\) 是**batch平均**，不是以前804-only诊断中的特殊系数。也不要在这里只处理4条，却错误地再除以100。

梯度累积需要在一个有效batch完成后才做参数更新；裁剪也应针对累计后的梯度，而不是每处理一条就各裁剪一次。PyTorch的相关示例也把这些操作放在有效batch边界处理。([PyTorch Docs][1])

**有效batch=4是起始建议，不是已验证最优值。** 先测最大的完整mesh能否前向、反向，以及显存、耗时；能稳定packed多条时可以优化执行方式，但不要中途悄悄改变有效batch和loss尺度。训练吞吐和可行batch应通过实际程序测量，不能只根据模型参数量估算。([谷歌开发者][2])

### 每步必须记录清楚三个计数

按上述方案：

$$
1\text{ epoch}=100\text{次mesh参与}=25\text{次optimizer更新}.
$$

因此：

| 训练量        | Optimizer更新 | 每条mesh被训练的次数 |
| ---------- | ----------: | -----------: |
| 4 epochs   |         100 |            4 |
| 100 epochs |        2500 |          100 |
| 200 epochs |        5000 |          200 |

**100条训练的5000次更新，不等于每条都训练了5000次。** 这也不能直接与此前单条804点的5000步比较。step预算与样本参与预算必须分别记录。([谷歌开发者][2])

## 五、学习率和第一段预算：先建立一条正常训练轨迹

### 建构学习率的起始方案

本轮不从单条末尾的精修LR起步。建议仍以随机初始化阶段使用过的量级作为候选：

| 参数组            |       第1次更新 |       第100次更新达到 |
| -------------- | ----------: | --------------: |
| Encoder＋μ      | \(10^{-6}\) | **\(10^{-5}\)** |
| Decoder＋两个head | \(10^{-5}\) | **\(10^{-4}\)** |

前100次optimizer更新线性warmup，之后先保持。它有已有单条建构实验作为起点，但**没有证明适合100条、batch4**，必须通过起跑记录检查；不按数据量增加100倍LR。原建构配置的确采用过这些端点。

### 第一段建议预算：200 epochs

按有效batch4计算，就是：

$$
\boxed{5000\text{次optimizer更新，共20000次完整mesh参与。}}
$$

这是**第一段联合学习观察预算，不是保证200 epochs内100条必然全对**。每条只参与200次，不能在预算末尾仅凭未全对就宣判容量不足。

前100次更新是这段预算里的起跑检查，不另起分支。检查数值有限、四个重建参数组实际更新、logvar不变、数据遍历和归约正确。没有工程异常就按固定配置继续，不因个别mini-batch loss上升临时调参数。

**正式启动这段预算前，先测完一次100条遍历的时间和峰值显存。** 目前还没有100条名单、尺寸分布和当前硬件预检，不能可靠地承诺总耗时。若预估超出预算，应在开跑前修改并记录预算，而不是运行中无记录地改设置。

## 六、验收要能回答老师的问题，而不是再堆平均曲线

建议在epoch **0、10、25、50、100、150、200**，固定当前checkpoint，做100条全量评价。逐条保留：

`UID、Edge FP/FN、实际Face FP/FN、缺失GT Face候选数、严格成功标记、Edge/Face loss`。

汇总至少显示：

> **Edge严格成功：**/100；Face严格成功：**/100；Edge＋Face联合严格成功：__/100。**

同时报告四项总FP/FN和仍未通过的mesh列表。**平均F1、平均loss只是辅助，不能用99条容易样本掩盖最后一条困难样本。**

早期随机预测可能形成很密的边图，使实际Face枚举成本很高。此时可以分块计算；若某次枚举因资源限制未完成，必须写“未完成”，不能用截断候选得到的结果冒充完整验收。Edge已经错误的mesh当然已确定联合验收失败，但其未算完的Face FP/FN不能填0。

一旦首次得到100/100，在预算内后续评价继续检查保持，并保存、重载同一个checkpoint再全量复核。**不拼接每条mesh在不同训练时刻的最好结果。**

## 七、后续路线就按100条目标推进，不再来回切换规模

$$
\boxed{
\text{固定100条、从头}\ \mu\text{重建}
\;\rightarrow\;
100/100\text{严格成功}
\;\rightarrow\;
\text{同一集合每步新}\epsilon\text{训练}
\;\rightarrow\;
\text{逐渐接入KL}
}
$$

μ阶段通过，只能写成“100条确定性重建overfit通过”，不是完整VAE已经通过。sampling与KL阶段另立预算，但**现在不用先设计一整套β扫描**。

原两条成功、804点诊断和数值排查全部归档保留；旧单条未完成的LR对照不再占据当前主线，也不需要先证明“任意小集合都快速成功”。

---

**现在实际要做的第一项任务是：生成并锁定100条manifest，使用当前512＋math00＋Soft4实现完成数据和资源预检，然后按固定协议启动fresh μ训练。**

**先把100条清单、规模统计和预检报告拿齐，再开第一段200 epochs；不是立即把旧单条命令的样本数改成100、步数改成10000就启动。** 这次要得到的是一条清楚、可持续执行的100-mesh训练主线，而不是继续围绕单条结果不断分叉。
